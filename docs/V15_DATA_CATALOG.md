# V15：Dynamic Data Catalog（动态数据目录）

## 这一步解决什么问题

以前调查规划器只能看到开发者手工写在工具注册表里的 `measure（指标）` 和 `dimension（维度）`。当数据库增加一个字段，或用户上传一个新的数据域时，模型可能不知道字段存在；反过来，模型也可能尝试使用实际不存在的字段。

V15 增加了一个只读的 **Runtime Data Catalog（运行时数据目录）**：每次调查前，系统从当前数据库的已发布数据和受允许的分析模型中读取元数据，整理出：

- `Dataset（数据集）`：数据集名称、所属数据域、数据来源、数据粒度和记录数。
- `Field（字段）`：字段名、观察到的数据类型、是否允许为空、空值比例和保守的用途判断。
- `Role（字段角色）`：`measure（指标）`、`dimension（维度）`、`identifier（标识）` 或 `unknown（待确认）`。
- `Alias（中文/别名）`：能够和版本化数据域定义匹配的中英文名称。
- `Data Gap（数据缺口）`：未登记的数据域只标为 `custom_candidate（自定义候选）`，不会被假装成标准域。

目录只返回元数据，不返回患者行、`payload_json` 或原始文本。它不是自由 SQL 接口，也不会因为发现了字段就自动赋予模型新的查询权限。

## 调查时如何使用

```text
实际数据库 / 已发布批次
        ↓
Runtime Data Catalog（字段、类型、粒度、域覆盖）
        ↓
语义指标和维度筛选
        ↓
LLM 生成 InvestigationPlan（调查计划）
        ↓
PlanValidator（计划校验器）重新检查工具、数据域和权限
        ↓
固定参数化只读工具执行
```

这里有两道门：

1. 目录门：只有当前数据中实际观察到的字段，才会被标为可用候选。
2. 能力门：即使字段存在，也必须有已注册的语义能力和受治理工具；目录不会把任意字段变成自由 SQL。

因此，未知字段的正确结果是“发现了一个候选字段，但当前没有安全分析工具”，而不是编造一条查询。

## 字段角色怎么判断

这是保守的工程提示，不是医学结论：

- 数字字段通常是 `measure（指标）`，但 `age（年龄）`、`visit_week（访视周）`、`month（月份）` 等时间或分层字段会保留为维度。
- 以 `id`、`key`、`sequence` 结尾的字段通常是 `identifier（标识）`；标识也可以作为分组维度使用。
- 日期、时间、布尔值、文本和枚举通常是 `dimension（维度）`。
- 混合类型或无法判断的字段标成 `unknown（待确认）`，不会强行转换。

正式分析仍由领域插件、指标定义和 SQL 工具负责；目录中的类型提示不能替代数据标准、统计方案或人工医学审核。

## API（接口）

### 读取 V15 目录

```http
GET /api/v15/clinical/catalog?trial_id=TRIAL-CF-101
X-InsightFlow-User: clinical-analyst-asia
```

可选参数：

- `trial_id（试验编号）`：返回当前身份可访问试验的目录，并按试验数据范围收窄。
- `published_batch_id（已发布批次）`：返回某一个已治理发布版本的目录；必须同时提供 `trial_id`。

返回的重点字段：

```json
{
  "catalog_version": "V15",
  "published_domains": ["ADEFF", "ADSL", "AE", "DM", "EX"],
  "measures": ["baseline_score", "week12_improvement_score", "adherence_rate"],
  "dimensions": ["site_id", "region", "arm", "visit_week", "sex", "severity_band"],
  "datasets": [
    {
      "dataset": "mart_week12_efficacy",
      "domain": "ADEFF",
      "record_count": 50,
      "fields": [
        {"name": "week12_improvement_score", "inferred_type": "number", "role": "measure"}
      ]
    }
  ]
}
```

接口中的 `measures / dimensions` 是数据库实际观察到的原始字段；发送给规划器前，运行时会再映射成受治理的语义名称（例如 `week12_improvement_score → treatment_effect / week_12_improvement`、`arm → treatment_arm`）。这样页面能如实展示数据库，模型又不会直接把原始列名当成 SQL。

## 前端学习入口

打开 `http://localhost:55173/`，左侧选择 **数据目录（Data Catalog）**。页面会先加载当前身份可访问的试验，再显示实际发现的数据域、记录数、字段类型和字段角色。

页面有意不显示患者级原始值；要看调查证据，应进入 **动态调查（Dynamic Investigation）** 并查看证据链和结论。

## 本版本的边界

- V15 解决“规划器不知道真实字段”的问题，不等于已经为所有新字段自动生成统计方法。
- 新数据域可以被发现并保留为候选，但要回答问题仍需增加领域定义、分析模型、工具和黄金问题。
- 目录失败时，调查会退回静态能力目录，并在审计信息中记录失败原因；不会因为目录探测失败而编造数据。
- 未绑定批次的分析模型不会被用于批次目录，防止默认数据泄露到用户指定版本。

## 真实分层如何进入调查

目录发现 `sex（性别）`、`severity_band（疾病严重度）`、`age_band（年龄段）` 后，规划器可以为每一个真实维度安排独立的 `stratify_measure（分层指标）` 任务。任务最终绑定到同一个受治理的 `build_subgroup_forest（亚组聚合）` 工具；服务端只允许 `region`、`site_id`、`age_band`、`sex` 和 `severity_band` 五个固定维度，并把维度名映射到固定 SQL 列名。模型不能把目录字段拼接成 SQL，也不能把不存在的维度当成证据。

如果问题同时要求性别和疾病严重度，系统会分别执行两个分层任务，再由结论模型逐项比较结果。某个分层单元格低于 10 例时，工具保留分层标识但抑制测量值，结论必须写明“无法判定”，不能把抑制当成零差异。

敏感性分析里的 `analysis_method（分析方法）` 是受治理的计算方式参数，不是数据库列；它由工具注册表校验，不要求在目录字段中出现。相反，年龄段、性别、严重度等真实数据维度仍必须先在目录中发现，并通过固定的只读列映射。按这些维度分析缺失率时，运行时只允许连接已列入白名单的 `dim_participants（受试者维度表）`，不会开放任意表连接。

缺失率是一个派生指标：它由 `week12_missing（Week-12 是否缺失）` 状态字段计算，而不是要求数据库必须有名为 `missing_rate` 的列。V15 的目录会把这种“由状态字段计算的指标”交给规划器；当问题要求按年龄段、性别或严重度解释缺失时，受治理工具会关联已授权的受试者维度。绑定上传批次而该维度没有同批次来源时，系统会报告数据缺口，不跨批次借用默认人口学数据。

下一步是根据陌生问题矩阵中真实出现的缺口，增加置信区间、正式缺失机制和多维交叉统计能力；这些工作属于后续 V16，不在 V15 中假装完成。
